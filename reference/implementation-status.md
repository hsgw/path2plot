# 実装状況(path2plot)

このファイルは実装フェーズの進捗管理台帳。フェーズ分けは [SPEC.md](./SPEC.md) のFR番号(機能要件)に対応する。実装作業の前後にこのファイルを確認し、該当フェーズのステータス/メモを更新すること。

方針: 「パスの単純な分解→gcode出力→パスの最適化・円弧処理→塗りつぶし処理→書き順→ペン分割→仕上げ」の順でコア機能を先に作る。パスの単純な分解・gcode出力の時点では単一ペン(色分割なし)を前提とし、ペン分割は最後に追加する。実機(Prusa MK3S)テストは各フェーズの検証で随時行う。

各フェーズの「テストデータ」で参照するサンプルSVGは `fixtures/phaseN/` 配下に用意済み。ユニットテストからも同じfixturesを再利用できる。

**メモ**

- `src/core/`にmatrix・transform属性パーサー・パス(d属性)パーサー・円弧(A)→ベジェ変換・図形(rect/circle/ellipse/line/polyline/polygon)→パスコマンド変換・ベジェ折線化・座標変換・stroke/fill解決・DOMParser統合(`svgParser.ts`)を実装。円弧(Aコマンド)は本フェーズのfixtureでは未使用だが、実データ対応のため標準的なendpoint→center parameterizationで変換する実装を含めた
- ベジェ折線化は「制御点を最終mm座標系まで変換してから許容誤差(mm単位)で折線化する」方式とした。アフィン変換はベジェ曲線を不変に保つため、この順序で正確な結果が得られる
- Vitestは`src/core/**/*.test.ts`(node環境)に限定されているため、DOMParserに依存する`svgParser.ts`自体はユニットテスト対象外とし、要求されている3項目(transform flatten・ベジェ折線化・座標変換式)のみをテストした。`svgParser.ts`の統合的な動作はdevサーバー+Playwrightでfixtures/phase1配下の全7ファイルを読み込んで目視・自動検証済み(unsupported-elements.svgで期待通り5件のエラー、malformed.svgで行/列付きエラー、その他は0件のエラーで正しい形状・位置に描画)
- プレビューのフィット(拡大縮小・中心合わせ)は新規ファイル読込時のみ再計算する仕様とした。毎回自動フィットすると、DPI/倍率設定を変更してもプレビュー上のサイズが変化して見えず、ユーザーテスト8が満たせないため
  - **設計変更(2026-07-13、Phase3後のUI改善)**: 上記の「コンテンツのbounding boxにフィット」方式は、DPI変更のたびにプレビューの拡大縮小・位置がズレて見づらいという指摘を受け、「想定描画可能領域(FR-35のbedWidthMm/bedHeightMm)に固定フィットする」方式に変更した。ビュー(白い用紙枠の位置・大きさ)はベッドサイズ設定とコンテナのリサイズのみに追従し、DPI/倍率設定やSVG内容には一切依存しない。用紙枠からはみ出したストロークはそのまま枠外(アプリ背景色の領域)にはみ出して描画され、FR-38のはみ出し警告と視覚的に対応する。詳細はPhase3セクションの`PreviewPanel`関連メモ参照
- **既定DPI値の変更(2026-07-13)**: `App.tsx`の`DEFAULT_SETTINGS.dpi`を96→**72**に変更した。実運用で読み込むSVGはIllustrator書き出しが主であり、Illustratorの標準的な座標系(1 user unit = 1pt = 1/72インチ)に合わせることで、読み込み直後からDPI設定を手動で変更しなくても正しい実寸で表示・G-code出力できるようにするため(参考: `fixtures/user/gcode_test.svg`の実測でDPI=72相当と判明)

- **UIリファクタリング(2026-07-13)**: エラー表示を`SettingsPanel`内のインライン表示から、画面上部に常時表示される`ErrorBanner`(新規`src/components/ErrorBanner.tsx`)に変更。設定列の開閉状態に関わらず視認できる(FR-41の警告表示パターンをFR-36のパース/要素エラーにも拡張)。手動で閉じられるが、エラー内容(signature)が変わると自動的に再表示される。FR-43のクリック/ホバー相互ハイライトやエラー文言の日本語整形は今回は対象外(見送り、要望があれば別途対応)
- **パフォーマンス改善(2026-07-31)**: `fixtures/user/city.svg`(5,831パス、863KB)のような大規模SVGで、読込〜プレビュー表示可能になるまでの時間が長くUIがブロックされる問題があった。原因はSVGパース(`parseSvgFile`)・塗りブロック生成(`buildFillBlocks`)・端点結合(`buildJoinedBlocks`、FR-14)がいずれもReactの`useMemo`内で同期実行されており、特に`buildJoinedBlocks`が全ストロークペア総当たりのO(n²)だったこと(詳細はPhase4のメモ参照、アルゴリズム自体は今回O(n)近傍探索に変更済み)。対策として`buildFillBlocks`・`buildJoinedBlocks`の2処理を新規`src/core/processing.worker.ts`(Viteネイティブの`new Worker(new URL(...), {type:'module'})`、追加ライブラリなし)にオフロードし、`App.tsx`は`postMessage`で依頼・`requestId`突き合わせで古い結果を無視する方式に変更した。処理中は新規`src/components/ProcessingOverlay.tsx`でフェーズラベル(塗り生成中/パス結合中)とパーセンテージのプログレスバーを表示する。`parseSvgFile`はWorkerに含めなかった: 実装当初は3処理すべてをWorker化する想定だったが、Playwrightでの実機検証(Chromium)で`DOMParser is not defined`が発生し、DedicatedWorkerGlobalScopeでは`DOMParser`が実際には利用できないことが判明した(TypeScriptの`lib.webworker.d.ts`にも`DOMParser`型は存在せず、`lib.dom.d.ts`限定)ため、SVGパース自体は従来通りメインスレッドの同期`useMemo`に残した。city.svgでの実機確認では、パース〜プレビュー表示完了までの体感時間が約1.3秒に収まり、進捗バーも意図通り表示・消滅することを確認した
  - 進捗バーはUI改善要望を受け、画面上部の帯状バナーから画面中央のポップアップ(半透明の背景+カード)に変更した(`ProcessingOverlay.tsx`、`.processing-overlay-backdrop`)
- **ステップ実行プレビュー(前へ/次へ/再生)のフリーズ解消(2026-07-31)**: 上記のWorkerオフロード後も、city.svg規模でステップボタン押下時に数百ms〜1秒近く描画が固まる問題が残っていた。調査の結果、ステップ変更ではパイプライン(Worker)は一切再実行されておらず、原因は**レンダリング側**にあると判明:
  1. `PreviewPanel.tsx`のCanvas描画が、step非依存の静的な「ゴースト表示(全ストロークの薄い背景描画)」を含めて毎ステップ全セグメントを描き直していた。加えて`ResizeObserver`を`draw()`呼び出しのたびに再生成しており、`observe()`の初回コールバックにより1操作でdrawが2回走っていた
  2. `StrokeListPanel.tsx`が`i >= step`の判定を全行に持ち、1クリックで最大1万数千個のReact要素を再生成・再照合していた(`React.memo`等はコードベース全体で未使用だった)
  - 対策: `PreviewPanel`を「ベースレイヤー(ベッド白塗り+ゴースト、stepに依存せず再描画しない)」と「アクティブレイヤー(ペンアップ破線+実色描画+開始点◯+方向矢印、stepで更新)」の2枚のCanvas([position: absolute](../src/App.css)で重ね合わせ)に分離し、アクティブレイヤーは「次へ」「再生」時(可視セグメント数が単調増加、かつsegments/表示サイズが不変)は新規区間のみを追記描画するようにした。「前へ」やファイル再読込・リサイズ時は従来通りフル再描画する。`toScreen`が毎点ごとに`Point`オブジェクトを新規確保していた箇所も、画面座標を直接返す`toX`/`toY`関数呼び出しに置き換えGCコストを削減した。`StrokeListPanel`は行コンポーネント(`StrokeRow`/`FillRow`/`JoinToggle`)を`React.memo`化し、`App.tsx`側でstepをそのまま渡さず`useDeferredValue`経由(低優先度・中断可能な更新)で渡すことで、巨大リストの再構築がCanvas更新をブロックしないようにした。`visibleSegmentCount`もO(N)の`slice`+`reduce`から累積和配列によるO(1)参照に変更。ついでに、ファイル読込のたび`joinOverrides`の`useEffect`リセットが新しい`Map`参照を作り、Workerへの`postMessage`が2回走っていた不具合も、空Mapの参照を使い回す方式に修正した
  - Playwrightでcity.svgを用いて実測(ヘッドレスChromium、クリックから2フレーム後のペイントまでの時間を計測): 「次へ」(追記描画)は修正前平均466ms→修正後平均66ms、「前へ」(フル再描画)は平均472ms→平均137ms(いずれも改善前後で同一手法により計測、詳細ログはコミットに含めず)。`fixtures/phase2/many-strokes.svg`・`fixtures/phase4/near-touching-endpoints.svg`で、開始点◯・方向矢印・ペンアップ赤破線・ゴースト表示・結合ブロックの視覚的な表現が変更前と同一であることをスクリーンショットで確認した

**FR-18の確定と塗りつぶし方式の拡張(2026-08-01)**

- **FR-18の残課題が解決した**。長く「ユーザーの意図した接続方法を実現できていない」としていた原因は、意図されていた軌跡が**`L0 → R1 → L2 → R3 …`(各行の左右の端点を交互に拾って斜めに繋ぐ一筆書き)**だったのに対し、過去2回の実装がいずれも「ハッチ線を描いた上で端点同士を繋ぐ」ものだった点にある。つまり**ハッチ線そのものは描かず、この斜めの折れ線自体が塗りになる**というのが本来の仕様で、2026-07-14に記録した「S点比較→E点接続→逆向き」という表現もこの軌跡を指していた
- 従来「ジグザグ結合」と呼んでいた挙動(ハッチ線を描き、隣接行の同じ側の端点同士を繋ぐ)は幾何学的には牛耕式(boustrophedon)の往復であり、真のジグザグとは別物のため **「往復(牛耕式)」** という別モードに改名・整理した。連結設定はチェックボックスから「連結しない / ジグザグ / 往復(牛耕式)」の3択セレクトに変更した(`HatchConnectMode`)

- **ジグザグ実装上の要点(柱への分解)**: ジグザグは1つの断片から端点を1つしか使わないため、素朴に「行の最左/最右点」を拾うと穴の反対側の断片が丸ごと描き残される。そこで隣接行の断片同士がx範囲で重なり、**かつその対応が1対1**のときだけ連結する分解(boustrophedon cell decomposition のセルに相当)を`hatchConnect.ts`の`buildColumns`に実装した。単純な連結成分(Union-Find)ではドーナツが上下のキャップ経由でつながって1グループになり分解にならないため、1対1であることを条件にしている。柱が1行しかない場合はジグザグを組めないため、例外的にその断片自体を1本の線として出力して描き残しを防ぐ
- **塗りつぶし方式の複数対応(FR-17の拡張)**: `FillSettings.pattern`(`'hatch' | 'concentric' | 'spiral'`)を追加した。ハッチには`crossHatch`(2方向を重ねる。方向をまたいだ連結はしない)と`waveform`(直線/正弦波/三角波、振幅・波長・分割数)をモードとして追加した。ジグザグは行の端点しか使わないため波形は結果に現れず、UIでも波形欄を出さない

- **同心オフセット・スパイラル**: `fillPolygon.ts`に`insetPolygonRaw`(破綻判定を伴わない素の内側オフセット)を追加した。既存の`offsetPolygon`は分裂を`split`エラー扱いするが、内側へ掘り進めば分裂・消滅は当然の結果なので同心塗りには使えないため。オフセットは前段の結果を再オフセットする累積方式ではなく毎回**元の輪郭から n×spacingMm** を一度に掘る(累積では丸め誤差が段数分たまる)。線間隔に極小値を入れられた場合の暴走を防ぐため、リング数はbbox対角長÷線間隔と絶対上限(同心2000/スパイラル500)で二重に抑える。スパイラルは同心リングを「現在の末尾に最も近い点」で切って開き順につなぐ簡易版で、半径を角度で連続補間する真の渦巻きは穴のある形状で成立しないためスコープ外とした。どちらも最も外側のリングが輪郭そのものなので、FR-21の輪郭線は二重描画になるため生成しない(UIでも設定を出さない)

**fill内部の書き順最適化(2026-08-01、同日の追加調整5)**

- ユーザー指摘「最適化が実行される場合、fillの内部も最適化される必要がある」への対応。従来のFR-15の最適化は塗りブロックを1ユニットとして扱うだけで、ブロック内部(輪郭ループ・塗り線)は常に生成順・生成時の向きのままだった。ブロックへ到達した位置と無関係な端から描き始める、輪郭線と塗り線の間を無駄に往復する、といった状態が残っていた
